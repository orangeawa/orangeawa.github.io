# 设计

## 状态驱动 UI

整体采用了 **状态驱动页面（State-Driven UI）** 的方式。

简单来说页面本身不负责维护核心业务逻辑，只是 `State` 的一种表现形式。当前题目、抢答状态、倒计时等数据都有统一的数据结构。

前端使用 `Pinia` 保存这些状态。无论数据来自 WebSocket 还是 HTTP 请求，都只负责更新 `State`，再由 Vue 的响应式系统驱动 UI 更新。

核心的状态结构大致如下：

```typescript
export interface GameState {
	/** 当前环节 */
	currentPhase: "waiting" | "required" | "snatch" | "risk" | "ranking";
	/** 当前正在进行的题号 */
	currentQuestionId: string | null;
	/** 抢答题倒计时时间戳 */
	snatchTimer: number | 0;
	/** 其他类型题目倒计时时间戳 */
	otherQuestionTimer: number | 0;
	/** 服务器时间戳 */
	serverTimestamp: number;
}
```

有了这层状态定义之后，交互就可以抽象成对 `GameState` 的修改, 来更新 UI。

## 抢答时效性

由于接收请求响应有时间延迟，要解决的问题就是: 倒计时怎么做到多端一致, 以及怎么判断"谁先按下的"

最直觉的做法是广播“还剩 5 秒”，不过网络传输速度本身不确定，每台设备也不一样。

所以下发的是截止的绝对时间戳，每个设备用各自的时钟去计算就能得到剩余时间

但还有个问题，每台设备的本地时钟也不准，所以还需要一个来自服务器的时间戳，本地计算好时间差

```ts
/**
 * 基于接收时刻和往返时延，估算服务器时间偏移量。
 */
export const estimateServerOffset = (
	serverTimestamp: number, 
	localReceivedAt: number, 
	roundTripMs:number = 0 
) =>  serverTimestamp - localReceivedAt + roundTripMs / 2

```

```ts
// 接收到 GAME_STATE 广播消息后进行处理
if (data.serverTimestamp) {
	clientTime.value = receivedTime;
	serverTimeOffset.value = estimateServerOffset(
		data.serverTimestamp,
		receivedTime,
		networkRoundTripMs.value,
	);
}
```

基于这个代码就能实现多客户端的同步

> 后来才知道正统做法是 `NTP` 那种四时间戳中点法

对于谁先按下这个问题，有了上面的代码就容易多了。

各端上报自己**相对于统一截止时刻的延迟**，比较延迟相对延迟大小。

```ts
const clickedAt = Date.now()
const pressDelayMs = clickedAt - snatchAnchor // snatchAnchor 是已换算到本地时钟的截止时刻
```

允许为负负数意味着在截止时刻之前就按了，于是同一个字段顺带解决了"提前抢答要扣分"的判定。

这个地方的漏洞也很明显，`pressDelayMs` 由客户端自己算，而客户端是可以撒谎的。不过对于这个小项目来说，作弊的可能性不大，所以就没有做额外的防护。
